# 术语卡模板

> Agent Atlas 的目标不是“翻译术语”，而是让第一次见到这个词的人能够建立正确直觉，并继续读懂更专业的材料。

## Term

`English Term`

**中文建议：**  
**成熟度：** 🟢 / 🟡 / 🔴  
**重要程度：** ★★★★★  
**学习阶段：** 入门 / 进阶 / 工程实践  
**最后更新：** YYYY-MM-DD

---

## 30 秒理解

用 2～4 句话回答：

1. 它是什么？
2. 它最核心的作用是什么？
3. 为什么 Agent 领域的人会频繁提到它？

这一部分必须做到：**没有计算机专业背景的人也基本能看懂。**

## 先建立一个直觉

不要急着下定义。先用一个生活场景、工作场景或简单故事，让读者在脑中形成画面。

例如：

- Model 像“大脑”；
- Tool 像“手里的工具”；
- Sandbox 像“允许你动手操作、但与外界隔离的工作间”。

类比只帮助理解，不应代替技术定义；如果类比存在边界，要明确指出。

## 为什么会出现这个概念？

回答它解决了什么真实问题。

推荐结构：

```text
原来的问题
    ↓
为什么普通 LLM / 旧方案不够
    ↓
这个概念提供了什么能力
```

## 技术定义

在已经建立直觉之后，再给出更严格的工程解释。

需要说明：

- 输入是什么；
- 输出是什么；
- 谁负责控制它；
- 它与模型、工具、环境、状态之间是什么关系；
- 如果行业尚无统一定义，要明确写出“边界仍在变化”。

## 它是怎么工作的？

如果这个概念涉及过程，用步骤解释。

```text
Step 1 → Step 2 → Step 3 → ... → 结束
```

如果适合，加入伪代码、状态图或 Mermaid 图。

## 在 Agent 系统中的位置

```text
Agentic System
├── Model
├── Context
└── Harness
    ├── Agent Loop
    ├── Tools
    ├── State
    ├── Runtime
    └── Sandbox
```

这里的树只是帮助建立认知，不要把一种实现方式写成唯一标准。

## 一个具体例子

不要只写抽象伪代码。尽量给一个读者能想象的真实任务，例如：

> “帮我找三家酒店，比较价格，然后把结果整理成表格。”

再指出这个术语具体发生在哪一步。

## 一个最小技术例子

使用伪代码或非常短的代码解释机制，而不是为了展示复杂代码。

```python
# pseudo code
while not done:
    result = model(context)
    observation = run_tools(result.tool_calls)
    context.append(observation)
```

## 最容易混淆的概念

建议使用对照表：

| 概念 | 核心区别 |
|---|---|
| A | ... |
| B | ... |

重点解释“为什么看起来很像”和“判断它们的最简单方法”。

## 常见误解

至少列出 2～3 个初学者高频误区。

例如：

- ❌ 有 Tool Calling 就一定是 Agent
- ❌ Agent 一定是完全自主的
- ✅ 自主程度是连续谱，关键在于系统是否允许模型根据反馈决定下一步行动

## 你什么时候会遇到这个词？

告诉读者它通常出现在哪里：

- Agent SDK 文档
- Coding Agent
- 多 Agent 系统
- Evals / tracing
- 研究论文

这样读者下次看到它时能快速定位语境。

## 成熟度说明

解释为什么标记为 🟢 / 🟡 / 🔴。

- 🟢：定义和用法相对稳定
- 🟡：行业普遍使用，但边界、命名或实现仍在演化
- 🔴：新兴说法，尚未形成稳定共识

## 参考来源

优先顺序：

1. 官方文档 / 官方工程博客
2. 原始论文
3. 标准或协议规范
4. 高质量技术文章

避免只引用二手解释。对快速变化的 Agent 术语，应注明资料日期并定期复查。
